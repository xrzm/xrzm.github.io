Cookie和会话安全

发表于2024-08-04|更新于2024-08-08

Cookie和会话简介

Cookie

是Web服务端发送给用户浏览器的一小段数据（用于标识用户），浏览器会存储这些数据，并在后续发往服务器的请求中带上它们。

但是将用户标识存放在Cookie或URL参数中都有个问题：在浏览器端，用户可以查看和篡改这些数据。

Session

解决上述的问题的最好办法就是将数据存储在服务端，并且为用户的数据分配一个随机的ID，在客户端仅存储这个ID，然后用户每次访问服务器都要带上这个ID，服务端用这个ID去查已存储的数据就知道当前的访问者是谁了，过程如图所示：

在这个过程中，服务端存储的这份数据称为Session，分配给客户端的这个随机ID称为SessionID。


Cookie属性

Cookie有多个属性，服务端在设置Cookie时可以设置相应的属性值，基本上每一个属性都和安全有关系

  1. Name和Value：

    • Name字段是Cookie的名称。
    • Value字段是与该名称对应的值。

  2. Domain：

    • Domain字段定义了可以访问此Cookie的域名。

  3. Path：

    • Path字段定义了Cookie的有效路径，即哪些URL路径下的资源可以访问此Cookie。

  4. Expires/Max-Age：

    • Expires字段指定了Cookie的绝对过期时间（以UTC时间为准）。
    • Max-Age字段指定了从设置时刻开始计算的秒数，在这段时间内Cookie有效。如果设置为负数，则表示浏览器关闭时Cookie会被删除。

  5. HttpOnly：

    • 如果设置为true，则只有HTTP协议可以访问该Cookie，JavaScript无法读取它，从而提高安全性。

  6. Secure：

    • 如果设置为true，则只有通过安全连接（如HTTPS）时才能发送该Cookie。

  7. SameSite：

    • 这是一个新的属性，用于控制第三方Cookie的行为。它可以设置为Lax、Strict或None。
    • None模式下，不进行任何限制。
    • Lax模式下，除非特定条件满足，否则不会发送第三方Cookie；
    • Strict模式下，完全禁止第三方Cookie；

  8. Priority：

    • 指定当存在多个优先级相同的Cookie时，哪个Cookie应该被优先发送。

安全使用 Cookie

现代 Web 应用广泛使用 Cookie 作为客户端的身份凭证，因此安全地使用 Cookie 非常重要。本节介绍 Cookie 使用过程中的安全建议。

1、正确设置属性值

  • 设置 Secure 属性：在 HTTPS 应用中，对关键的 Cookie 设置 Secure 属性，确保它仅在加密连接中传输。否则，攻击者可能通过 HTTP 协议诱导受害者访问，导致 Cookie 明文传输被窃听。
  • 避免设置 Domain 属性：如果不需要让子域名读取 Cookie，不要设置 Domain 属性，这样 Cookie 仅限于当前域名可读取。如果需要共享登录状态，确保所有子域名安全。
  • 设置 HttpOnly 属性：大多数 Cookie 不需要被客户端 JavaScript 代码读取，特别是重要的 SessionID。设置 HttpOnly 属性可以减少 XSS 漏洞带来的 Cookie 泄露风险。
  • 设置 SameSite 属性：对于与会话相关的 Cookie，建议将 SameSite 属性设置为 LAX，以减少 CSRF 攻击风险。但不能完全依赖该属性，应显式指定重要 Cookie 的 SameSite 属性。

2、Cookie 前缀

在存在子域名的网站中，每个站点都可以通过设置 Cookie 的 Domain 属性写入一个让所有子域名可见的 Cookie。为解决此问题，浏览器实现了 “Cookie 前缀” 安全方案，Web 应用可以为 Cookie 名称添加特定前缀，以满足特定要求：

  • Host- 前缀：Cookie 名称包含此前缀时，必须满足以下条件：

    1. 带有 Secure 属性
    2. 不包含 Domain 属性
    3. Path 属性为 “/“
    4. 当前为 HTTPS 连接

  • Secure- 前缀：Cookie 名称包含此前缀时，必须带有 Secure 属性且当前连接为 HTTPS。

浏览器会拒绝不满足这些条件的带前缀的 Cookie。带 “Host-“ 前缀的 Cookie 不能包含 Domain 属性，确保 Cookie 与域名绑定，只能由当前域名植入。


3、保密性和完整性

  • 保密性：Cookie 对用户是公开的，使用浏览器开发者工具可以查看所有 Cookie。因此，Web 服务端不能将机密数据写入 Cookie。

  • 完整性：由于用户可以轻松修改 Cookie 内容，Web 服务器应将 Cookie 视为不可信的外部输入数据。例如，不要通过 Cookie 值判断用户身份或角色。更安全的做法是将重要数据保存在服务端，或对 Cookie 数据进行加密或签名。

  • 部署建议：在子域名众多且安全性不受控的情况下，建议为关键 Cookie 添加 “Host-“ 前缀，确保其仅限于当前域名使用，避免被其他子域名影响。

通过这些措施，可以显著提高 Web 应用中 Cookie 的安全性。


会话安全

在Web应用中，会话的本质是标识不同的访问者，并记录他们的状态。

会话管理

  1. 会话ID的随机性：

    • 不能简单地使用用户的ID、时间戳等数据作为SessionID，也不能基于用户公开的信息简单计算出一个值。
    • SessionID要足够长，防止攻击者使用穷举法破解。

  2. 会话的过期和失效：

    • 自动过期：设置会话的有效期，在用户长时间不活动后自动失效。
    • 手动失效：用户注销时，立即销毁会话。

  3. 绑定客户端：

    • IP 地址绑定：将会话与客户端IP地址绑定，防止会话劫持（这个更安全）。
    • 浏览器绑定：将会话与浏览器（UA头）绑定，增加安全性。

  4. 安全传输：

    • HTTPS：使用 HTTPS 保护会话ID在传输中的机密性，防止中间人攻击。
    • Secure 属性：设置 Secure 属性，确保 Cookie 仅在加密连接中传输。

  5. 客户端存储会话：

    • JWT：本质上是带签名的JSON数据，有必要的情况下也可以对它进行加密。

固定会话攻击

前面已经提到：用于标识会话的SessionID是个随机值，攻击者是没有办法进行猜测的。

但是在一些场景中，攻击者可以诱导用户使用攻击者指定的SessionID，当受害者登录成功后，这个SessionID就关联了受害者的身份，相当于攻击者拥有了受害者在目标网站上的身份。这种攻击就叫固定会话攻击，如图所示：

在攻击过程中有一个关键的步骤，就是让受害者使用攻击者的SessionID，有几个方法可以实现这一步：

  1. 跨子域名Cookie设置：恶意子域名应用可以设置一个在其他子域名也生效的Cookie，从而控制其他应用中的SessionID。
  2. 跨端口或路径Cookie设置：同一个域名在不同端口或路径下运行多个应用，恶意应用可以写入在其他应用中有效的Cookie。
  3. URL参数：一些应用允许通过URL参数指定SessionID，攻击者可以诱导受害者点击带有SessionID参数的链接。
  4. XSS或CRLF注入：存在XSS或CRLF注入漏洞的应用中，攻击者可以植入特定的Cookie来实施固定会话攻击。

为了防止固定会话攻击，当用户的登录状态发生变化后，服务端应该为用户生成一个新的SessionID，以杜绝固定会话攻击。
