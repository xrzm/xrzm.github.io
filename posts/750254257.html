深入了解同源策略

发表于2024-08-08|更新于2024-09-09|web

同源策略详解

同源策略（Same-Origin Policy，有些文章将”origin“称为“域”，比如将“cross-origin”称为“跨域” ）是Web浏览器的一种核心安全机制，用于限制不同源网站之间的互相访问，防止敏感信息泄露。 所谓“同源”，指的是协议、域名和端口号都相同。

注意：

  • 同源策略并不是用于保护网站服务器安全的，要防的也不是网站的访问者；防御的是恶意网站——防止它们读取用户在当前网站上的数据，或以用户的身份向当前网站发起操作。（这是贯穿于前端安全的基本原则）
  • 网页跨域嵌入资源，甚至跨域“写“操作，都是被允许的，但就是不能通过JavaScript代码跨域读取内容


同源策略的三个要素

  1. 协议：指网页使用的网络通信协议，如HTTP或HTTPS。
  2. 域名：指网页的主机名部分，不包括子域名。
  3. 端口：指网页所使用的端口号，如果未指定，则默认为80（HTTP）或443（HTTPS）。

下表展现了不同URL与http://store.company.com/dir/page.html进行同源对比：

URL 结果 原因
http://store.company.com/dir/other.html 同源 只有路径不同
http://store.company.com/dir/inner/another.html 同源 只有路径不同
https://store.company.com/secure.html 不同源 协议不同
http://store.company.com:81/dir/etc.html 不同源 端口不同
http://news.company.com/dir/other.html 不同源 主机名不同

站点隔离

理论上，有了同源策略的限制，任何网站都不能在浏览器中获取其他站点的数据，但是任何代码都有漏洞，如果同源策略在实现上存在漏洞，将带来不可估量的危害。

为此，Chrome提供了”站点隔离“特性，它确保了不同站点的页面被放在不同的进程中渲染。

站点隔离可以看成同源策略之后的另一道防线，即使攻击者找到漏洞，能绕过同源策略，但他还是被限制在只渲染当前站点的沙箱进程中，无法获取其他站点的数据，这种做法就是典型的纵深防御的体现。

同源策略和站点隔离的区别

保护范围

  • 同源策略主要针对脚本和资源的访问控制，防止跨源访问
  • 站点隔离通过进程隔离来保护数据

实现方式

  • 同源策略通过检查URL的协议，主机名和端口来决定是否允许访问
  • 站点隔离通过在浏览器中为不同站点分配独立的进程来实现物理上的隔离

跨域DOM互访问

同源策略有严格的跨域访问限制，但是在很多应用场景中，网站有跨域访问的需求。

第一种情况是前端不同源的页面之间的DOM互访问，这种情况不涉及服务端，是前端两个页面之间的数据交互。

子域名应用互访问

如果一个公司有多个子域名，并且不同的子域名之间需要进行交互，在这种场景下，同源策略允许将限制放宽：

通过修改两个子域名页面的document.domain属性使其在同一个源内，这两个页面就可以访问对方的DOM内容了。

注：document.domain属性用于设置当前文档的原始域部分，常用于同源策略。现已被弃用，因为它破坏了同源策略所提供的安全保护，并使浏览器中的源模型复杂化，导致互操作性问题和安全漏洞。

例如：www.example.com和login.example.com是example.com的子域名，如果在这两个网页中通过JavaScript设置document.domain为example.com，那么它们就能互相访问对方的DOM内容。

但是修改时有几点需要注意：

1、修改document.domain时，浏览器会做安全检查，只允许将其修改为当前域名或者父域名，否则会抛出异常。

2、修改document.domain的同时会把当前源的端口置为”NULL“。

3、在JavaScript代码中使用赋值语句document.domain=document.domain;时, 虽然没有修改域名,但当前页面源的端口被置为”NULL”,它的源其实已经被改变了,所以这么做也会受到其他子域名应用的威胁

下表展示了父域名页面与子域名页面设置不同 document.domain属性时的访问结果

URL 当前页面设置的 document.domain iframe 中的 URL iframe 页面设置的 document.domain 结果
http://www.example.com example.com http://login.example.com:81 example.com 允许访问
http://www.example.com example.com https://login.example.com example.com 禁止访问（协议不一样）
http://www.example.com example.com http://example.com 未设置 禁止访问（端口不一样）
http://www.example.com example.com http://www.example.com 未设置 禁止访问

修改当前页面的document.domain属性虽然带来了便利,但是也带来了安全风险:

当修改后的域名还存在多个子域名时,如果其中某些子域名应用的安全不受自己控制,或者存在漏洞,那么可能会直接威胁当前域名应用的安全。

所以说,虽然通过document.domain实现跨域访问DOM在现代浏览器中都可用,但是这种方式已经不推荐使用了,更安全的做法是通过window.postMessage来实现。


通过window.name跨域

window.name 属性用于保存当前窗口的名称。

利用 window.name 跨域的原理是：一个窗口在设置了 window.name 的值后，即使跳转到不同的域，该属性的值仍然保留。

如果一个页面通过 iframe 加载一个跨域页面，跨域页面可以修改 window.name 的值，然后再跳转到与父页面同域的页面。这样，父页面就可以读取该值，实现跨域数据传输

iframe：该标签定义了一个内联框架，被用于在当前文档中嵌入另一个文档

需要注意的是，window.name 的初衷并非用于跨域数据传输，但如果其中存储了敏感数据，那就存在数据泄露的风险。恶意网站可以通过读取 window.name 属性，从而获取前一个页面的数据。

因此，一些现代浏览器在跳转到不同源的网站时，会将 window.name 属性置空，以防止数据泄露。综上所述，window.name 并不是推荐的跨域数据传输方式。


window.postMessage

window.postMessage用于一个页面向另一个窗口发送信息，而无需这两个窗口共享相同的源。这种方法主要用于解决JavaScript跨域问题，可以实现页面与嵌套的iframe、页面与其打开的新窗口以及多窗口之间的消息传递。

通过 window.postMessage 发送和接收信息时，应特别注意以下两点：

  1. 限制目标窗口源：避免将目标窗口的源设置为 "*"，因为这允许任何源接收信息，存在安全隐患。如果目标窗口被重定向到恶意网站，这样的信息传递会暴露给不可信任的接收方。

  2. 验证信息来源和内容：接收方在处理信息前，应验证信息来源，确保来自可信站点。同时，对收到的数据进行严格的格式校验，尤其是在将数据作为 eval() 函数的参数或用于构建 DOM 节点时，否则可能会引发 DOM 型 XSS 漏洞。


跨域访问服务端

前面的案例讲的是两个不同源的前端页面互访问，还有一种场景是前端页面需要从跨域的服务端获取数据。以下是几种常见的跨域访问方案：

JSONP方案

JSONP（JSON with Padding） 是一种早期的跨域请求方式，主要用于绕过浏览器的同源策略限制。

其基本原理是通过 <script> 标签引入一个跨域的 JavaScript 文件，文件内容包含被请求的 JSON 数据。由于 <script> 标签不受同源策略的限制，服务器返回的数据可以在客户端执行，并通过回调函数（Callback）传递给 JavaScript。

JSONP方案其实不算跨域传输数据的标准做法，是能算是个技巧，而且它只能实现单向的读操作（只支持GET请求），写操作则需要借助其他方案才能实现。

使用JSONP方案时，有以下几个安全注意事项：

  1. 不要在JSONP中包含敏感数据。

  2. 为了阻止不可信的源调用，服务端要拒绝不带Referer头的JSONP请求。

  3. 只有确保另一个域是安全可信的，才能使用JSONP跨域传输。

  4. 在响应头中需要设置Content-Type为application/javascript；否则，在大部分Web应用中默认响应的Content-Type为text/html，恶意构造的回调函数名可导致XSS风险。

  5. 在一些不用于跨域访问，只响应JSON/XML数据的接口中，不要加上JSONP需求，否则可能带来安全隐患。


跨域资源共享（CORS）

CORS（Cross-Origin Resource Sharing） 是目前最广泛使用的跨域访问解决方案。它通过设置 HTTP 头，允许服务器声明哪些域名能够访问其资源，允许的 HTTP 方法，以及自定义头部信息。浏览器会根据 CORS 头的设置，决定是否允许跨域请求。

CORS的工作原理

当 JavaScript 使用 XMLHttpRequest 或 Fetch API 发起跨域请求时，浏览器会在请求中自动附加一个名为 Origin 的头部，用以标识请求的源域名。服务器在响应中需要返回一个 Access-Control-Allow-Origin 的头部，以指示哪些域名被允许访问。如果 Origin 与服务器允许的域名匹配，则请求成功；否则，浏览器会抛出错误。


在CORS（跨域资源共享）中，请求被分为简单请求和复杂请求。这两种请求的主要区别在于是否需要进行预检请求。

简单请求

简单请求是不需要预检请求的请求类型。简单请求满足以下条件：

  1. HTTP方法只能是GET、HEAD或POST。
  2. 请求头只能包含Accept/Accept-Language/Accept encodings、Content-Type（仅限”application/x-[www-form-urlencoded]“、”multipart/form-data“、”text/plain“）、 authorization等特定字段。
  3. 不包含任何自定义的头部字段。

对于简单请求，浏览器会直接发出CORS请求，在头信息中增加一个Origin字段，表明请求的来源。


预检请求

预检请求（Preflight request）是一种特殊的CORS请求，用于确认服务器是否允许特定类型的跨域请求（避免请求被直接发出去而给服务端带来副作用——增、删、改数据）

当浏览器检测到一个非简单请求时，它会自动发起一个OPTIONS请求作为预检操作。如果预检请求成功，浏览器才会发送真实请求；否则，浏览器会阻止该跨域请求。

具体实现机制

CORS预检请求的实现机制主要通过以下几个步骤和关键HTTP请求标头来完成：

  1. 检测跨域请求：当浏览器检测到一个跨域请求时，它会自动发出一个OPTIONS请求。
  2. 发送预检请求：这个OPTIONS请求包含了几个重要的HTTP请求标头：
    • Origin：用于指定发起请求的源（如域名、协议或端口）。
    • Access-Control-Request-Method：用于询问服务器是否允许使用特定的请求方法（如GET、POST、PUT等）。
    • Access-Control-Request-Headers：用于询问服务器是否允许包含特定的自定义头信息。
  3. 服务器响应预检请求：服务器在接收到这个OPTIONS请求后，会返回一组响应头信息，这些响应头信息包括对CORS的支持情况和允许的请求方法。具体来说，服务器会返回以下响应头：
    • Access-Control-Allow-Origin：指定哪些源可以访问资源。
    • Access-Control-Allow-Methods：允许使用的请求方法。
    • Access-Control-Allow-Headers：允许的请求头信息。
  4. 确认并执行实际请求：如果预检请求成功通过服务器的验证，浏览器将知道可以安全地发送实际的跨域请求（如POST、GET等）。此时，浏览器会再次发送实际的请求，并附带必要的请求头信息。
  5. 处理无响应的情况：如果服务器没有明确回应预检请求，或者返回了错误的响应，浏览器可能会阻止后续的实际请求，并向开发者提供错误信息。

复杂请求

复杂请求则需要先发送一个预检请求来确认服务器是否允许该请求。只有得到肯定答复，浏览器才会发出正式的XMLHttpRequest请求，否则就报错。


安全性注意事项

请求中的 Origin 头部由浏览器自动设置，网页无法通过 JavaScript 修改其值，因此恶意站点无法伪造 Origin。

另一个与安全相关的 CORS 响应头是 Access-Control-Allow-Credentials：

  • 当其值为 true 时，表示服务器允许客户端发送凭证信息（如 Cookie、Authorization 头或客户端 TLS 证书）。
  • 如果此头部不为 true，而客户端将 XMLHttpRequest 对象的 withCredentials 设置为 true，则该跨域请求会失败，客户端无法获取响应内容。

常见错误配置及其风险

在 CORS 中，Access-Control-Allow-Origin 头部用于定义允许访问的源域名，以下几种配置可能带来严重的安全风险：

  1. 明确允许的域名：当服务器返回 Access-Control-Allow-Origin: https://example.com 并且设置 Access-Control-Allow-Credentials: true，意味着允许该域名访问并携带凭证信息。如果该域存在 XSS 漏洞，会扩展至当前站点，因此必须对所有信任源进行安全评估。

  2. 星号“*”：Access-Control-Allow-Origin: * 允许任何源访问，但浏览器不允许发送凭证信息。这虽然避免了一些安全风险，但仍可能导致未经身份验证的数据泄露。如果应用依赖其他认证方式，如 IP 白名单，仍存在被攻击的风险。

  3. “null”：设置 Access-Control-Allow-Origin 为“null”非常危险。它允许本地文件、Data URL 或沙箱化的 iframe 页面访问当前源，这可能导致任意本地文件或恶意页面窃取数据。

  4. 多个子域名的支持：Access-Control-Allow-Origin 不支持通配符（如 https://*.example.com），且在需要凭证访问时不能设置为“*”。简单复制请求中的 Origin 值到响应头中，可能会导致任何源都能带凭证信息进行跨域请求，从而暴露安全漏洞。

  5. 白名单校验：对于支持多个来源的跨域访问，必须严格校验请求中的 Origin 是否在白名单中。如果需要支持多个子域名，应仔细设计白名单逻辑，以防误通过恶意域名的请求。


结论

CORS 已成为跨域访问的标准，本质上是一种跨域授权策略。服务端通过 CORS 策略定义哪些源可以访问、是否可以携带凭证、允许的 HTTP 方法和头部信息等，浏览器则负责执行这些策略，并阻止违反策略的行为。


私有网络访问

私有网络访问（Private Network Access，PNA） 是一种针对私有网络的跨域请求方法。PNA 是一个相对较新的浏览器功能，旨在保护从公共互联网上的网页向私有网络或本地网络发送的跨域请求。

特点：

  • 适用于访问本地设备或内网资源，例如路由器、打印机、IoT 设备等。
  • 私有网络请求需要额外的安全措施，例如配置 CORS 允许特定的外部源访问内网资源。
  • 未来可能会要求使用 HTTPS 才能访问私有网络，以进一步提高安全性。

WebSocket跨域访问

WebSocket 是一种在单个 TCP 连接上进行全双工通信的协议。与传统的 HTTP 不同，WebSocket 不受同源策略的限制，因此可以跨域访问。

特点：

  • 使用 WebSocket 协议（ws:// 或 wss://）进行通信，不依赖于 CORS。
  • 适合需要实时通信的应用场景，如聊天室、在线游戏、实时通知等。
  • WebSocket 连接建立时可以包含一些与 CORS 类似的安全措施，例如 Origin 头部的验证。
